# Handoff: review findings (2026-09-28)

Written by a Claude Code session that read the repo on a Windows machine
(it could not run anything there: no Linux, no ffmpeg). Everything below
comes from reading code and the recorded run logs. **No tests or runs were
executed for this review.** Verify claims against the code before acting.

Branch reviewed: `fix/analysis-download-bounds` (HEAD `d2f33b8`), which is one
commit ahead of `master` (`eedb911`). Line numbers refer to that branch.

## Goal of the project (from the owner)

Take an informal request ("cinematic clips of horses grazing") and return
high-quality clips that match it. Current pain: frequent errors that need an
AI agent to fix things mid-run, and very long run times.

## Headline

The pipeline spends almost all its time and complexity re-checking video,
while the parts that find good footage are thin and low-yield. The model
calls are not the bottleneck.

Evidence: `benchmark/improvement/live-first.json` (2 clips, one command,
1210 s active):

| Stage | Seconds | Share |
|---|---|---|
| analyze | 674 | 56% |
| export | 274 | 23% |
| discover | 60 | 5% |
| label_tiles + label_strips (14 model calls) | 44 | <4% |

Analyze processed 2 sources x 60 s of footage in 674 s.

## Findings: speed

1. **One yt-dlp process per small span.** Each kept storyboard tile becomes a
   window of one storyboard interval (`_windows_for_times`,
   `src/scenery_brief_clips/vision.py:62`), padded 2 s each side
   (`analysis_plan`, `analyze.py:143`). Every span is a separate
   `fetch_analysis` call → yt-dlp startup, player/JS challenge via node,
   ffmpeg download. Startup cost is paid per ~10-14 s piece.
2. **`--force-keyframes-at-cuts` re-encodes every analysis span**
   (`yt.py:655`). The Brazil run log blames this path for ffmpeg reading
   through a 23-minute source to get a 14 s piece.
3. **The same frames are decoded 5-7 times**: `validate_analysis_media` full
   decode (`yt.py:184`), SHA-256, PySceneDetect decode (`detect.py`),
   continuity decode per excerpt (`continuity.py`), review frame extraction
   (`review.py`), `verify` full decode (`verify.py:97`, ~36 s per call in the
   benchmark), then export re-downloads, full-decodes, encodes, and
   `verify --require-export` decodes again.
4. **Analysis and export download the same 720p content twice.** Analysis is
   ≤720p H.264 video-only; export is the 720p rendition with `-copyts`. Docs
   forbid reuse for timestamp-provenance reasons. Worth revisiting: fetch once
   (stream copy + copyts, slightly wide span) and use that file for both.
5. **Export is serial** (`export.py:917`), ~137 s per clip in the benchmark.
6. **Default 4 analyze workers** (`pipeline_analyze.py:185`) on a host with
   1.6 GB RAM. The Brazil run swapped to a halt; it only finished with
   `SCENERY_ANALYZE_WORKERS=2`.
7. **Stalled spans still cost up to ~10 min each** after the branch fix:
   300 s timeout (`cli.py:763`) x 2 acquisition attempts
   (`pipeline_analyze.py:163`), and there is no overall deadline for a run.

## Findings: why runs break and need an agent

1. **Planner prompt contradicts its validator.** `PLANNER_INSTRUCTION`
   (`brief.py:198`) says to use "close names" and allows strategy `synonym`;
   `validate_query_plan` (`brief.py:267`) rejects any query that lacks a
   subject noun verbatim. The model is never told this rule, and there is no
   retry with the validation error. One paraphrase = whole run blocked. This
   is exactly what happened in the Brazilian military run (agent hand-wrote
   the queries).
2. **The one-command runner can't plan live, and the skill doesn't use it.**
   `run-pipeline` stops without `--plan` because the CLI never wires the live
   planner (`runner.py:539`; CLI only wires vision, `cli.py:1160`). The skill
   (`.hermes/skills/scenery-clips/SKILL.md`) never mentions `run-pipeline`;
   it walks 18 manual steps with background jobs and polling. That is where
   the agent babysitting comes from.
3. **Rigid brief form.** `validate_brief` accepts only duration band 4/6/12
   (`brief.py:125`), export height exactly 720 (`brief.py:141`), geography
   `null` or `"european"` (`brief.py:118`). "2-8 seconds" is not expressible.
   Every field also needs provenance quotes, which is error-prone for an
   agent to fill.
4. **Branch/skill mismatch.** The hang fix exists only on this branch, but the
   branch's own skill step 1 says to stop unless HEAD == origin/master.
   Master's `vision.yaml`/`planner.yaml` are `codex-login`/`gpt-6-sol`; this
   branch switched both to OpenRouter `z-ai/glm-5.3-flash`.
   `tests/test_vision_wire.py` asserts on the live config file, so changing
   the model breaks a test.

## Findings: why results fall short

1. **Quality is judged on storyboard tiles** (tiny, ~160x90). Nothing measures
   sharpness, bitrate, shake, burned-in text or watermarks, so "cinematic /
   high quality" is not really checked.
2. **One `keep` tile promotes the whole video** (`apply_tile_scores`,
   `vision.py:134`), so weak sources reach the expensive stage.
3. **Windows are too short for edited footage.** A moment needs ≥4 s without a
   cut after 0.3 s edge trims, inside a ~10-14 s window. In the Brazil run: 30
   moments rejected upstream, 7 of 18 sources had zero excerpts.
4. **Brief exclusions are not enforced** (documented in ISSUES/ARCHITECTURE).

## Findings: repo hygiene

- ~10.4k lines of src, ~9.6k lines of tests (390 tests), ~2.9k lines of docs.
  Most recent work added checks/provenance rather than speed or yield.
- Docs contradict each other (STATUS still names gpt-6-sol as the vision wire;
  SEARCH_BRIEF.md says "not implemented"; README/ARCHITECTURE hard-code
  `/root/projects/...`).

## Recommended plan (in order)

Measure first: record a baseline of a small fixed run (stage timings from
`runner_state.json`, excerpts produced, clips delivered) before changing
anything, then compare after each step.

1. **Merge the download fix to master**; default `SCENERY_ANALYZE_WORKERS=2`;
   add an overall run deadline; cut the per-span timeout to something scaled to
   span length.
2. **Acquire once, decode once.** One stream-copy download per selected region
   (drop `--force-keyframes-at-cuts`), reused by analysis and export. One
   decode pass producing scene cuts, continuity samples and review frames.
   Drop redundant full-decode validations, or keep one.
3. **Wider, fewer regions.** Merge nearby kept tiles into 30-60 s regions;
   require ≥2 kept tiles (or a keep ratio) before a video goes to analysis.
4. **Fix the planner.** State the exact-subject rule in the prompt; on
   validation failure retry once with the error text; wire the live planner
   into `run-pipeline`.
5. **Loosen the brief form**: any duration band within sane limits
   (e.g. 2-15 s); fewer mandatory provenance fields.
6. **Make the skill one command**: `run-pipeline --live-vision` with the
   agreements passed up front.
7. Later: a real quality signal on review frames (sharpness/blur, text or
   watermark detection) instead of storyboard tiles alone.
